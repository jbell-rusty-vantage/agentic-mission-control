## Mental model restated

**After round A (2026-10-24).** The system we are designing is the target, not a patch on today's
runtime. A mission agent does domain work with admitted knowledge tools; the only Mission Control
responsibility it keeps is to say which of its results fulfil which obligation (the exact act is settled
in round B). Trusted origin never comes from the agent: the lane builds it from the live attempt, hands
it into the knowledge call through a Mission Control gateway under a credential minted for that
invocation, and the knowledge service checks it before it plans or writes. Anything an agent reaches
without that gateway is standalone work in its own run namespace and cannot fulfil an ingestion
obligation. Every piece of knowledge carries seven separable facts: who first produced it, who is
calling now, which native receipt proves the effect, which revision it is, who adopted it as a
deliverable, who assessed it, who consumed it. Reusing a report adopts it; it does not re-ingest it or
re-author it. Both application knowledge data models and the Knowledge Services ingestion, verification
and report modules are inside the prerequisite migration, so that an evidence-backed report is one
model with a PostgreSQL binding and a Neo4j binding. Owner's correction to the interviewer: stop
reconciling with the current code; design the best system and name the migration to it.

**After rounds B to F (2026-10-24), the model the owner confirmed (OC-D105).** An author writes a goal
with a binding, two obligations (`assertions`, `report`) with five named guarantees, and a transfer
profile for the next agent. The agent gets domain tools for that binding, the filesystem, and one act:
`submit_output`. Every knowledge call leaves the agent through a Mission Control gateway that attaches
the live invocation origin and a credential minted for that invocation; the knowledge service binds the
origin from the credential, puts it inside the native intent digest before planning, and refuses a payload
that disagrees. Effects are keyed once; a lost response is reconciled by that key, never retried blind.
Tools return qualified handles; the agent names handles or file paths per obligation; the harness
completes coordinates only when exactly one binding in scope resolves a bare id, reminds once, auto-
finalizes only single matches, repairs once, then blocks. A file and a native report are two things
until receipt-backed lineage says the report was registered from that file. Every deliverable carries
seven separable provenance roles; adopting is not producing. Knowledge Services gets one Knowledge
Operation Protocol, one evidence-backed report core (`research-report.v2`) with a PostgreSQL binding
inside it and a Biotech binding that speaks Biotech's own executor protocol, one VerificationRun with
one sealed manifest, and step contracts whose semantic steps a KS executor or a mission agent may host.
The next agent receives state and accepted assertions inline, the exact body as a probed read-only file
named in a mount index, evidence as handles, and starts only after a readiness receipt; the same module
serves the next iteration, a dependent stage and a linked mission. Before any of this runs, the
migration programme A0 → {A, B, D} → {A3, B3, B4} → C changes both application schemas, the common
release and Knowledge Services; the owner expects to find more Mission Control tables in that pass.
Owner's refinement to the interviewer (OC-D103): depth has at least two categories, the agent-facing
representation and the codebase modules; both are confirmed.

### What the audit settles before any question is asked

1. "Just inject the mission ID" is not available on either application. AI Engineer's columns are
   foreign keys to its own orchestration rows; Biotech accepts the id but does not authenticate it and
   keys its lineage on `(system, runId)`, not on the mission.
2. The trusted coordinates exist in Mission Control at the hook seam and in the binding, but the
   values a tool could read are the template's, not the live attempt's. That is a kernel defect to
   fix before any origin can be derived from them.
3. Exact retrieval is weaker than the checkpoint assumed on both sides: AI Engineer's `report_get` is
   not a snapshot read and may return an unsealed package; Biotech has no report body custody and no
   retrievable retained read.
4. Both services have receipt lookup by their own key (receipt id; effect key), and both record native
   lineage (`report_ingestion_link`; `Activity` + marker). The bridge ingredients exist; the bridge does not.
