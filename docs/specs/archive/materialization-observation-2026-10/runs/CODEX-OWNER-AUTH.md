# Codex selected-home auth and 0.162.1 schema handoff

MO-65 requires `owner_cli_login` to use `MISSION_CONTROL_CODEX_HOME_MODE=owner` and an explicit `MISSION_CONTROL_CODEX_OWNER_HOME` on the worker's filesystem. An isolated home cannot inherit a ChatGPT login. The harness refuses the incompatible route before workspace acquisition and again on reattach. An admitted API-key route remains valid with an isolated home. Projected hooks still require isolated home; owner-login plus projected hooks is an explicit unsupported combination, not permission to write the owner's trust configuration.

The owner must establish any login interactively on the selected host/home. This change never starts login, opens a browser, copies auth.json, reads credential contents, installs Codex or changes global config. `adapters.codex.auth_preflight.owner_login_preflight` probes only `codex login status` with the exact selected CODEX_HOME, a minimal environment and API keys scrubbed first. Its result contains a boolean/reason/home/route, not raw CLI output. Preflight must use this helper after normal auth admission; file presence alone does not prove authenticated readiness.

Integrator joins:

1. In host/bootstrap readiness, after admitting Codex auth, call `require_auth_home(admitted.route, settings.mission_control_codex_home_mode, selected_owner_home)` and map its typed code into a blocking PreflightIssue. For owner route, await `owner_login_preflight(actual_linux_binary, selected_owner_home)`; fail if not ready. Use the selected worker's Linux binary, not the native Windows receipt below.
2. In general launch-binding/admission checks, reject owner login with isolated worker-home configuration using the same topology guard. No canonical binding field/digest change is needed. Runtime prepare/reattach already guard this before a provider session.
3. Refresh shared describe/launch selection pins for newly authored Codex bindings to 0.162.1 / v2@0.162.1. Preserve existing sealed binding bytes and historical 0.162.0 fixture tree.
