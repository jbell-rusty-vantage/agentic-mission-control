## Q1. Cloud environments (Claude Code on the web)

Source unless stated: https://code.claude.com/docs/en/cloud-environments (C-ENV), https://code.claude.com/docs/en/claude-code-on-the-web (C-WEB).

- **Plans**: "Cloud sessions are available on Pro, Max, and Team plans, and for Enterprise users with premium seats or Chat + Claude Code seats." Usage "counts toward your plan's usage limits ... there's no separate charge for the cloud VM." (C-WEB). ZDR or HIPAA orgs cannot use cloud sessions (C-WEB).
- **Definition**: an environment = name, network access level, environment variables (`.env` format), setup script; on Pro/Max also *network secrets* (edit dialog only). (C-ENV "Configure your environment").
- **Create/edit/archive is UI-only**: "Create, edit, and archive environments from the environment selector ... at claude.ai/code ... or from the prompt box in the Desktop app." "There's no settings page or direct URL for the selector." "`/remote-env` only sets the default: it doesn't start a session, and it can't add or edit environments." "You can't delete an environment, only archive it." Shared (org) environments: Owner, admin page "Cloud environments" (Team/Enterprise). **No public API for Anthropic-hosted `env_` environments** (VERIFIED absence in docs; the only environment HTTP API is the self-hosted pool API `POST/DELETE /v1/code/runners/self-hosted/pools`, beta `ccr-byoc-2025-07-29`, per repo revalidation S5 and https://code.claude.com/docs/en/self-hosted-environments-testing "Create a dedicated test environment").
- **Default environment**: onboarding creates **Default** (Trusted network, no vars, no setup script) via `/web-setup` or Pro/Max web onboarding; Team/Enterprise shows a form unless Owner enabled "Quick setup". (C-ENV)
- **Selection**: web/desktop/mobile selector; Owner org default; Projects use project setting; CLI uses `remote.defaultEnvironmentId` (written by `/remote-env`), else the Anthropic-hosted env, else first non-bridge env. `--environment <id>` accepts only self-hosted `ccpool_` IDs: "Claude Code rejects Anthropic-hosted `env_` IDs passed to the flag, so use `/remote-env`". (C-ENV)
  - Settings reference: `remote.defaultEnvironmentId` scope **"Any file"** ("For a self-hosted environment ID, user or managed settings, or the `--settings` flag only"), and C-ENV: the `/remote-env` pick applies "unless the same key is set at a higher-precedence settings layer, such as a repo's project settings." → an `env_` can be pinned per repo via committed `.claude/settings.json`, and by precedence via `--settings` (CLI-arg layer). https://code.claude.com/docs/en/settings-reference#remote-defaultenvironmentid. Per-invocation `--settings` for `env_` remains **UNVERIFIED by drill**.
- **Network levels**: None / Trusted (default allowlist: Anthropic, GitHub/GitLab/Bitbucket, container registries, cloud SDK hosts, npm/PyPI/RubyGems/crates/Go/Maven/etc., Ubuntu, Datadog/Honeycomb intake, `*.modelcontextprotocol.io`) / Full / Custom (own list, optionally + defaults, `*.` wildcard). Changes apply to running sessions "within about a minute". Always reachable regardless of level: GitHub via its proxy, MCP connectors (via Anthropic servers), network-secret hosts, Anthropic API ("even at None"). No org-wide allowlist; no server-managed setting adds domains. (C-ENV "Network access")
- **Env vars**: readable by "anyone who uses the environment"; read at session create and on every VM restore/rebuild; edits reach an existing session only at next restore/rebuild. `OTEL_*` vars are consumed by Claude Code and not passed to commands. Session sets `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` itself (user value ignored). (C-ENV)
- **Network secrets** (Pro/Max only; not Team/Enterprise "yet"; not self-hosted; not with CMEK): bearer/custom-header credential attached by Anthropic's agent proxy to listed hosts after leaving the VM; never attached to GitHub, Anthropic API/public registries, setup-script requests, or Claude Code's own telemetry export. Add/delete only in UI; can't edit or view after save. (C-ENV "Add network secrets")
- **Image**: fresh VM per session, Ubuntu 24.04 x86_64; Python 3.x (pip, poetry, uv, black, mypy, pytest, ruff), Node 20/21/22 (22 on PATH; npm, yarn, pnpm, bun, eslint, prettier, chromedriver), Ruby 3.1–3.3, PHP 8.3, OpenJDK 21 + Maven/Gradle, Go, Rust, GCC/Clang/cmake/ninja/conan, docker/dockerd/compose, PostgreSQL 16, Redis 7.0 (not started), git, gh, jq, yq, ripgrep, tmux. `check-tools` prints versions. Base image cannot be replaced ("isn't supported yet"). (C-ENV "Installed tools")
- **Limits**: ~4 vCPU, 16 GB RAM, 30 GB disk; Bash 2 min default / 10 min max foreground, then auto-backgrounded up to 30 more min (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`); SessionStart `command` hook 600 s default (not enforced with `async: true`); setup script cached only if it finishes in ~5 min; VM pauses after a few idle minutes, can be reclaimed (history restored, background work/subagents/self-paced `/loop` not). (C-ENV "Time limits", C-WEB "Environment expired")
- **Setup script caching**: runs as root before Claude Code launches; must exit 0; filesystem snapshot reused by later sessions; rebuilt when script or allowed hosts change or after ~7 days; not re-run on idle restore. (C-ENV "Environment caching")
- **SessionStart hooks & detection**: SessionStart runs after launch on every start/resume, local and cloud; scope cloud-only work with `if [ "$CLAUDE_CODE_REMOTE" != "true" ]; then exit 0; fi`. Session ID in `CLAUDE_CODE_REMOTE_SESSION_ID` (`cse_...`; URL form `session_...`). Commits get a `Claude-Session: <url>` trailer and PR bodies the URL unless `attribution.sessionUrl: false`. (C-ENV)
- **Settings honored in cloud** (https://code.claude.com/docs/en/settings#settings-in-cloud-sessions, C-ENV "What carries over"): repo `CLAUDE.md`, `.claude/rules/`, `.claude/skills|agents|commands/` YES; repo `.claude/settings.json` hooks/permissions/env and `.mcp.json` YES **only in single-repository sessions** (multi-repo sessions read only `enabledPlugins`/`extraKnownMarketplaces` keys — and still don't load them); server-managed settings YES (not Claude Tag); user `~/.claude/*`, `settings.local.json`, device managed-settings/MDM NO; repo-declared plugins/marketplaces NO; transport vars (`NODE_EXTRA_CA_CERTS`, mTLS) ignored; claude.ai-enabled skills and connectors YES. A setup script may write `~/.claude/CLAUDE.md` for user-level instructions.
- **Commands in cloud**: text-output built-ins work (`/compact`, `/context`, `/model sonnet`, `/fast`); `/plugin`, `/resume`, `/clear` unavailable; `/schedule` refused inside a cloud session. (C-WEB "Manage context"; https://code.claude.com/docs/en/routines Troubleshooting)

### Claude Managed Agents (Claude Platform API)

Base URL B = https://platform.claude.com/docs/en/managed-agents/ . All endpoints need `anthropic-beta: managed-agents-2026-04-01` (B+overview). Status: beta, "enabled by default for all API accounts"; not ZDR/HIPAA-eligible (B+overview). Spot-checked items marked (SC).

- **Harness**: "Pre-built, configurable agent harness that runs in managed infrastructure" (B+overview, SC). Not described as the Claude Code CLI; migration guide maps `CLAUDE.md` → agent `system`, hooks → `always_ask` permission policy or client logic; slash commands/plan mode move to the client (B+migration). Repo `.claude/skills/*/SKILL.md` can be loaded from a mounted GitHub repo ("load them from a GitHub repository mounted on the session", B+skills, SC). `.claude/agents`, `.claude/settings.json` hooks, `.mcp.json` honored: **UNVERIFIED / not documented** (treat as no).
- **Resources**: Agents `POST /v1/agents` (`name`, `model`; `system`, `tools`, `mcp_servers`, `skills`, `multiagent`, `metadata`), versioned with optimistic `version` (B+agent-setup). Environments `POST/GET /v1/environments`, `GET/DELETE /v1/environments/{id}`, `POST .../archive` (B+environments). Sessions `POST /v1/sessions` (`agent` {id, version} or `agent_with_overrides`, `environment_id`, `resources`, `initial_events` ≤50, `budget.max_list_cost`) (B+sessions); retrieve/list/update/archive/delete (B+session-operations). Session resources `/v1/sessions/{id}/resources` (B+github). Events `POST/GET /v1/sessions/{id}/events`, `GET .../events/stream` (SSE) (B+events-and-streaming). Vaults `/v1/vaults`, `/v1/vaults/{id}/credentials` (B+vaults). Files API with `scope_id=sesn_...`; outputs under `/mnt/session/outputs/` (B+files). Custom skills `POST /v1/skills` (B+skills). Memory stores `/v1/memory_stores` (B+memory). Scheduled deployments (Deployments API, cron) (B+scheduled-deployments, SC). Self-hosted sandbox work queue `/v1/environments/{id}/work/{poll,ack,heartbeat,stop,stats}` (https://platform.claude.com/docs/en/api/beta/environments/work).
- **Sandbox**: fresh Linux container per session, Ubuntu 24.04 x86_64, ≤8 GB RAM, 10 GB disk; Python 3.10–3.13, Node 20–22, Go, Rust, Java 21, Ruby, PHP, git, Postgres/Redis (not running), Playwright+Chromium, docker "limited availability" (B+cloud-sandboxes-reference). `packages` (apt/cargo/gem/go/npm/pip), cached per environment. Networking `unrestricted` (default if omitted in API) or `limited` with `allowed_hosts`, `allow_package_managers`, `allow_mcp_servers` (B+environments). No plaintext env-var block; secrets via vault `environment_variable` credentials substituted on egress (B+vaults). Environments are **API-creatable and editable** — unlike Claude Code `env_` environments. CPU, max lifetime, idle retention: UNVERIFIED.
- **Git**: `github_repository` resource (`url`, `authorization_token`, optional `mount_path` under `/workspace`, `checkout` branch|commit); multiple repos; token rotatable; repo set fixed per session. Branch/commit/push/PR documented via the **GitHub MCP server** (`https://api.githubcopilot.com/mcp/`) with a vault MCP credential (B+github, SC: "With the GitHub MCP server, the agent can create branches, commit changes, and push them"). Plain `git push` from bash with the mount token: UNVERIFIED.
- **Tools/policy**: `agent_toolset_20260401` (bash, read, write, edit, glob, grep, web_fetch, web_search), custom tools (client-executed, `user.custom_tool_result`), remote MCP only (HTTP/SSE; tunnels in research preview), skills (anthropic/custom, ≤500/session), `multiagent_20261001` (subagents, dynamic workflows/workflow runs, advisor) (B+tools, B+multiagent-orchestration, B+workflow-runs). Permission policies `always_allow` | `always_ask` | `auto`, answered by `user.tool_confirmation` (allow/deny + `deny_message`) — a **durable server-side approval wait** (B+permission-policies). No hooks (B+migration).
- **Control/observe**: client events `user.message`, `user.interrupt`, `user.custom_tool_result`, `user.tool_confirmation`, `user.define_outcome`, `system.message`. Status `idle | running | rescheduling | terminated`; stop reasons `end_turn`, `requires_action` (+`event_ids`), `budget_reached`. SSE carries only events after connect; reconnect = list history (`created_at[gt|gte|lt|lte]`, `types`, `order`, `page`, `limit`) and dedupe by event id (B+events-and-streaming, /api/beta/sessions/events/list). Archive requires idle ("A `running` session cannot be archived; ... send a `user.interrupt`", B+session-operations, SC). Agent/tools updatable only while idle. `ant beta:sessions connect <id>` terminal/`--web` viewer; scripts use `ant beta:sessions:events stream|send` (https://platform.claude.com/docs/en/cli-sdks-libraries/cli/sessions-connect, SC).
- **Webhooks**: Console-registered, `whsec_` signed; payload is `type`+`id` only (fetch the object); events include `session.status_run_started`, `session.status_idled`, `session.status_rescheduled`, `session.status_terminated`, `session.thread_terminated`, budget/outcome events (B+webhooks, SC). Up to 3 delivery attempts, unordered (per helper; retry count UNVERIFIED by me).
- **Usage/billing**: session `usage` + `session.usage` events (B+session-observability). Pricing: model tokens + "Session runtime | $0.08 per session-hour | `running` status duration" (https://platform.claude.com/docs/en/about-claude/pricing, SC). API key (Console) billing; claude.ai subscription not documented as an option (treat as API-only). Rate limits 300 create / 1,200 read rpm per org (B+reference).
- **Outcomes**: `user.define_outcome` rubric graded by separate grader, `max_iterations` default 3, max 20 (B+define-outcomes).

**Assessment for a "claude_cloud" lane.** Managed Agents satisfies nearly every MP-16 item the Claude Code cloud product lacks: API create with idempotent-reconcilable list, status, replayable paged events, follow-up, interrupt, archive/delete, durable tool approval, per-session usage and budget cap, webhooks, API-managed environments/secrets/skills/files. Gaps: it is **not Claude Code** (no `.claude/agents`, hooks, settings, `.mcp.json`, plugins; only repo skills and a `system` prompt), git push/PR is via GitHub MCP not a proxy, API-key billing only (not the owner's subscription), beta. The repo's RESEARCH.md explicitly forbids "unrelated OpenAI/Anthropic managed-agent services" as the `claude_cloud` production lane and the 10-09 revalidation lists Managed Agents as non-qualifying; using it requires an owner decision to define a **separate lane profile** (e.g. `claude_managed_agents`), not a re-qualification of `claude_cloud`.

## Q3. Secrets / env vars in cloud

- Environment variables: UI only, plaintext-readable by every user of the environment; warned against for secrets (C-ENV).
- Network secrets: Pro/Max only, UI only, proxy-attached per host, not attached to telemetry/GitHub/registries/setup script (C-ENV).
- `GH_TOKEN`/`GITHUB_TOKEN`: if unset, read as placeholder `proxy-injected`; if set, passed through as ordinary env var (C-ENV "Work with GitHub issues and pull requests").
- `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` set in a cloud environment do not override subscription credentials: "Cloud sessions always use your subscription credentials." https://code.claude.com/docs/en/authentication
- Collector credentials for OTel must go through server-managed settings (org Owner), not env vars (monitoring-usage).
- **No API** for environment variables or secrets on Anthropic-hosted environments (VERIFIED absence: docs describe UI/admin-page only).
- Managed Agents has a Vaults API — see Q2 Managed Agents.

## Q4. Git access in cloud sessions

- Two GitHub connection methods: Claude GitHub App (public repos + private repos it's installed on; required for Auto-fix, GitHub triggers, Projects) or `/web-setup` (sends local `gh` token to the claude.ai account; doesn't install the app or enable webhooks). (C-WEB, routines)
- GitHub proxy: VM gets a scoped credential; proxy swaps for the real token; rejects branch deletion and non-branch pushes (tags); does **not** restrict which branches are pushed (use rulesets); API scope = repositories attached to the session (others → 403 "`is not enabled for this session`"); **GraphQL blocked** (so `gh pr`/`gh issue` fail; use `gh api` REST). (C-ENV "GitHub proxy")
- Branches: routines push to `claude/`-prefixed branches unless the prompt directs otherwise; branch protection applies to the connected GitHub identity, so a rule it can bypass doesn't block. (routines "Repositories and branch permissions")
- Multiple repos: routines and the web UI accept several repositories; `claude --cloud` is single-repo. Multi-repo sessions skip repo hooks/permissions/env/`.mcp.json`. (C-WEB, C-ENV, settings)
- Non-GitHub: `CCR_FORCE_BUNDLE=1` uploads a git bundle (<100 MB, no untracked files; native Windows uploads uncommitted tracked changes unfiltered) but can't push back. GHES supported on Team/Enterprise. (C-WEB)
- Attribution: commits/PRs appear as the connected GitHub user; auto-fix replies under the user's account labeled as Claude Code. (C-WEB, routines)

## Q6. Worktrees and parallelism

- `claude --worktree|-w [name|#PR|PR URL|MR URL]` → `<repo>/.claude/worktrees/<name>`, branch `worktree-<name>`; `--tmux`; `worktree.baseRef` fresh|head; `worktree.sparsePaths`. `.worktreeinclude` (gitignore syntax) copies files that are also gitignored; skipped when a `WorktreeCreate` hook replaces git logic (non-git VCS). `WorktreeCreate`/`WorktreeRemove` hook events. https://code.claude.com/docs/en/worktrees, /cli-reference.
- Subagent `isolation: worktree`: per-subagent worktree, auto-removed if unchanged (D+sub-agents). Not in Python `AgentDefinition` → only via file-based agents loaded with `setting_sources`.
- Agent teams: experimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; interactive only (not `-p`/SDK per helper); cloud via environment variable (C-WEB). https://code.claude.com/docs/en/agent-teams
- Background sessions / agent view: `claude --bg [--agent X] "<prompt>"` returns the session id; `claude agents --json [--all]` is "the supported way to read session state from a script"; `claude attach|logs|stop|rm|respawn <id>`; supervisor process survives terminal close and sleep; `/fork`. Local machine only. https://code.claude.com/docs/en/agent-view
- Agent SDK: `cwd`, `add_dirs`; worktree allocation is the caller's job (Mission Control's managed worktree policy fits). Resume by `session_id` across processes (repo 10-07 note still valid).
- Cloud: each session = fresh VM + clone, branch isolation by session (`claude/...` for routines); parallelism by starting multiple sessions (`claude --cloud` x N, Projects threads); rate limits shared across the account (C-WEB). Upload path refuses sparse-checkout worktrees and `worktree.sparsePaths` worktrees (C-WEB).

## Q7. Callbacks / observation

- **HTTP hooks from a cloud VM**: hooks fire in cloud sessions ("Claude Code fires the same hook events wherever it runs", D+hooks, per repo S7); `type: "http"` POSTs the hook JSON to `url` with `headers` (env interpolation limited to `allowedEnvVars`). Egress follows the environment's network level: Trusted blocks custom hosts → use Custom (add our domain) or Full. Credentials for our endpoint: env vars are readable by all environment users; on Pro/Max a **network secret** for our host is attached by the agent proxy to "requests for the hosts you list" — whether Claude Code's own HTTP-hook requests traverse the agent proxy (vs. its telemetry export, which explicitly does not) is **UNVERIFIED**. Synchronous within timeout (600 s default); `async: true` for fire-and-forget. Only in single-repo sessions (or via server-managed settings hooks, Team/Enterprise).
- **Useful push events**: `SessionStart`, `UserPromptSubmit`, `PreToolUse`/`PermissionRequest` (gate), `PostToolUse`, `SubagentStart/Stop`, `Stop` (`last_assistant_message`), `StopFailure`, `Notification`, `SessionEnd`, `PreCompact/PostCompact`, `TaskCreated/Completed`. The self-hosted test recipe uses exactly a Stop hook POSTing to the driver ("swap the file write in the Stop hook for a POST to an endpoint your driver listens on", https://code.claude.com/docs/en/self-hosted-environments-testing). Correlate with `CLAUDE_CODE_REMOTE_SESSION_ID`.
- **Local stream**: `claude -p --output-format stream-json --verbose [--include-partial-messages] [--include-hook-events] [--forward-subagent-text] [--replay-user-messages] [--input-format stream-json]`; SDK equivalents `include_partial_messages`, `include_hook_events`, `forward_subagent_text`; `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` for `session_state_changed`. Not available for cloud sessions (`stream-json` unsupported with `--cloud`). (D+cli-reference, C-WEB)
- **OpenTelemetry** (D+monitoring-usage): `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_TRACES_EXPORTER`, `OTEL_EXPORTER_OTLP_{ENDPOINT,PROTOCOL,HEADERS}`, `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT`, `OTEL_METRICS_INCLUDE_SESSION_ID`, `OTEL_METRICS_INCLUDE_ENTRYPOINT`, `OTEL_RESOURCE_ATTRIBUTES`; traces beta `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`; inbound `TRACEPARENT` honored by `-p`/SDK. Metrics `claude_code.session.count`, `lines_of_code.count`, `pull_request.count`, `commit.count`, `cost.usage`, `token.usage`, `code_edit_tool.decision`, `active_time.total`. Events `user_prompt`, `assistant_response`, `tool_result`, `tool_decision`, `api_request`, `api_error`, `plugin_loaded`, `skill_activated` (list partial). Spans `claude_code.interaction`, `llm_request`, `tool`, `tool.execution`, `tool.blocked_on_user`, `hook`. Cloud: set via server-managed `env` (Owner; required if the collector needs a credential) or environment variables; collector host must be allowlisted; attributes `session.id`, `ccr.session.id`, `organization.id`; telemetry export never gets network secrets. Push-only, best-effort, no replay.
- **Outbound webhooks from cloud sessions**: none documented besides hooks/OTel (UNVERIFIED absence). Routines: none. Managed Agents: yes (Console webhooks, see Q2).
- **Notifications**: `Notification` hook; claude.ai/mobile push for cloud sessions (UI). Channels (push events *into* a running local session from an MCP server) are local-session only (https://code.claude.com/docs/en/channels).

## Q8. Manual-only prerequisites before automation can launch cloud sessions

1. A claude.ai subscription: Pro, Max, Team, or Enterprise (premium or Chat + Claude Code seat). Not ZDR/HIPAA org. (C-WEB)
2. Team/Enterprise: Owner enables `allow_remote_sessions` (Claude Code admin settings), Routines toggle, and GitHub connection methods / Quick setup. (C-WEB, routines)
3. GitHub: install the Claude GitHub App on each repo (needed for GitHub triggers, Auto-fix, Projects, and to clone instead of bundle-upload with `--cloud`) and/or run `/web-setup`. (C-WEB)
4. Environment: create/configure in the claude.ai environment selector (network level, vars, setup script, network secrets); pick CLI default with `/remote-env` or commit `remote.defaultEnvironmentId` to the repo. (C-ENV)
5. Routine path: create routine in web UI (or `/schedule`), add API trigger and generate token **in web UI only** (shown once). (routines)
6. CLI path: interactive `claude auth login` with a claude.ai account on the automation host; **refresh grant capped at 30 days**; `claude setup-token` (one-year, inference-only) does **not** carry `user:sessions:claude_code`; headless re-provision via `CLAUDE_CODE_OAUTH_REFRESH_TOKEN` + `CLAUDE_CODE_OAUTH_SCOPES` subject to the same cap; "Contact your Anthropic account team if you need a machine-identity path". (https://code.claude.com/docs/en/self-hosted-environments-testing "Authenticate from CI")
7. Telemetry: allowlist the collector host on the environment; credentialed collector requires server-managed settings (Owner; Team/Enterprise). (monitoring-usage)
8. Managed Agents path instead: Console org + API key, beta header (see Q2 MA).

## Q9. Billing / auth

Whether owner-only self-automation of the SDK on a Max plan is "ordinary, individual usage" is **UNVERIFIED** (no explicit ruling; ask Anthropic sales/support for a written answer).
