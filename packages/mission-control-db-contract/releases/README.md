# Additive component releases

`../component/` preserves the complete frozen **1.4.0** release. New versions live
in explicit version directories here. Select a component with `--component-root`;
there is no implicit `latest` alias, and this layout does not change deployment locks.
These version directories are the only release authority (Sprint V SV-17, plan row D0): the root
`../component/` is retired input kept for the historical tests and preparers, and is never a
build, lock or install source.

## 1.4.1

`1.4.1/component/` contains the byte-identical 1.4.0 migration prefix plus:

- `0042_codex_01621_lane_describe.sql`: Codex CLI 0.162.1, conditional on the exact
  old unqualified describe. The SQL retains the reviewed Codex-only candidate
  bytes and its historical proposal header. Build and installation state are
  established by the manifest and installer attestations, never that comment.
- `0043_cursor_cost_observation_contract.sql`: adds
  `mc.cursor-cost-observation/1` to the runtime document contract CHECK, retaining
  its ten previous contracts, other constraints, RLS, grants and immutable trigger.
- Release seed compatibility includes `mc.catalog.artifact-schemas`; the new
  common bundle requires component `>=1.4.1 <2.0.0`.

The sibling `1.4.1/runtime/` preserves the descriptor bytes and its relative path.
The predecessor fingerprint includes 1.4.0, enabling an attested additive upgrade
while retaining historical migration receipts.

From the repository root, `scripts/prepare_run2_release.py --out <fresh-directory>`
reproduces the input tree and refuses existing destinations. It wraps the original
Codex-only preparer, verifying the frozen 1.4.0 manifest and every input digest.
The default destination is this exact `releases/1.4.1/` directory; other destinations
inside the package are refused. Preparation produces no manifest or generated
contract. Build with the existing installer only against an explicitly authorized
disposable PostgreSQL 17 server:

```powershell
.venv/Scripts/mission-db.exe release-build --component-root packages/mission-control-db-contract/releases/1.4.1/component --admin-dsn-env MCDB_RELEASE_ADMIN_DSN
```

The build allocates a fresh `mcdb_release_*` database and drops it. The committed
manifest and generated contract record the resulting release inputs and schema.
Tests in `tests/integration/postgres/test_run2_release_141.py` use fresh `mct_*`
databases with the real installer for fresh install, 1.4.0 upgrade, seed application
and replay, drift refusal, preserved receipts, RLS and immutable guards. Their
temporary locks do not replace `deployments/*/release.lock.json`.

Local build and tests do not upgrade live installations or qualify a provider lane.

## 1.5.0

`1.5.0/component/` is the byte-identical **built 1.4.4** prefix (0001..0049, every input
verified against the 1.4.4 manifest) plus the Sprint V knowledge-boundary records (SV-13,
design M05). It is deliberately prepared from `releases/1.4.4`, never from the frozen 1.4.0
root `component/` that ends at 0041 (finding E10 / plan row D0): a source without 0042..0049
would silently drop the cognition-point and transcript tables.

- `0050_knowledge_operations.sql`: `knowledge_operation_journal`, one row per scoped
  `effect_key` (`prepared -> dispatched -> applied | noop | partial | rejected | uncertain`,
  `prepared -> rejected`, `uncertain -> dispatched` for a retry), with the frozen-after-dispatch
  `originating_origin`, `bound_effect_digest`, `current_caller_origin`, dispatch/envelope and
  remote handle fields, receipt reference and remote retry-after/revision. No credential
  column; origins carrying credential keys fail a CHECK. A guard trigger fixes identity, the
  legal edges and the receipt of a settled operation; every version appends one immutable
  `knowledge_operation_transition` row. Same key with a different bound effect raises
  `EFFECT_CONFLICT` (SQLSTATE `MCE01`) from the insert trigger and from the race-safe,
  invoker-rights `admit_knowledge_operation(jsonb)`.
- `0051_content_lineage.sql`: append-only `content_lineage` with the seven SP-10 provenance
  roles as a CHECK, a role/actor-kind matrix, at most one producer per subject, and no producer
  fact for an adoption.
- `0052_source_bindings_retained_observations.sql`: append-only `context_source_binding`
  (exact report/assertion handles, revision and digest per invocation) and
  `retained_read_observation` (observed digest, generated `digest_verified`, `readable`).
- `0053_submissions.sql`: `output_submission` (`submit_output`; stable `submission_key` per
  invocation and obligation, a revision is a new row, frozen selection, assessment
  `pending -> assessed | held | rejected`, `held -> assessed | rejected`; a changed selection
  under the same key raises `SUBMISSION_CONFLICT`, SQLSTATE `MCE02`) and the append-only
  `invocation_finalization` (one per invocation).
- `0054_transfer_plans_delivery_receipts.sql`: `context_transfer_plan` (frozen items, required
  digests and budget; only the state advances), append-only `context_delivery_receipt`
  (delivered, generated `digest_verified`, readable, budget fit) and `context_delivery_outbox`
  (runtime inserts; the outbox worker leases and acknowledges only, as for `outbox`).

All ten tables carry the installation/application/tenant scope with forced row security,
grants only to the existing runtime roles (no DELETE for any of them), table comments, and
no foreign key outside the common component (application stores are joined by receipt or
effect key and digest, never by key). Advanced transfer/accumulation fields are left to the
later output-contracts release.

**Why 1.5.0 and not 1.4.5.** 1.4.1..1.4.4 used patch numbers, including for new tables.
This release is selected from its actual compatibility instead: it only adds objects (no
existing table, constraint, grant, describe or seed contract changes; reader/writer protocol
stays `mission-control-runtime/1`; seed ranges `<2.0.0` still hold), so every 1.4.x reader
keeps working on it, but it introduces a new capability family that the knowledge gateway
and `submit_output` runtime will require. That is a backwards-compatible feature addition,
a SemVer minor, and `>=1.5.0` names the floor a runtime needs. Runtime bindings still pin an
exact `required_component_version`; deployment locks are unchanged by this release.

`scripts/prepare_release_150.py` reproduces the input tree from the built 1.4.4 inputs
(verified against its manifest, including the presence of 0042..0049) and refuses existing
destinations. Build as for 1.4.1 with
`--component-root packages/mission-control-db-contract/releases/1.5.0/component`. Proof:
`tests/integration/postgres/test_sprint_v_release_150.py` (fresh install and upgrade from
1.4.4 with preserved receipts and documents, verify and idempotent re-apply, journal
idempotency and `EFFECT_CONFLICT`, legal and illegal transitions, appended history,
immutability for runtime and owner, cross-tenant isolation, lineage, submission, read,
transfer and delivery-relay rules). Building it makes 1.5.0 the newest built release the
repository fixture installs.

## 1.7.0

`1.7.0/component/` is the byte-identical **built 1.6.0** prefix (0001..0055, every input verified
against the 1.6.0 manifest) plus one migration (Sprint OC WI-01 / OVE-163; OUTPUT-CONTRACTS §§2-4,
ADR-0058):

- `0056_output_contracts_and_fulfillment.sql`:
  - `output_promise_set`: the admitted set of a run with its closed completion (the only
    completion evaluated); `output_obligation_pin`: the revision an invocation pinned at start,
    never moved by a later activation, and required by every output revision it submits.
  - `output_obligation_revision`: one immutable revision of a run's named output promise (form,
    enforcement, evaluation scope, canonical `OutputObligation@2` document and digest, promise set
    and configuration digests); revision 1 carries no proposal, every successor carries its governed
    proposal (delegation, reason, expected prior) and the boundary kind it waits for; it stays
    pending until `output_obligation_head` advances to it (by one, compare-and-set) with an
    `activated_boundary_ref` of exactly that kind.
  - `output_revision`: one immutable exact output revision per deliverable of a submission act
    (canonical candidate, content digest, producer and caller origin refs), revision numbers dense
    per run, promise and deliverable, scope-checked against its `output_submission` row.
    `output_accepted_head`: the accepted revision of one deliverable, moved only by expected-head
    compare-and-set, never to an older execution generation, never deleted.
  - `output_set` / `output_set_member`: immutable pinned frontiers (promise revisions and exact
    members, each guarded to be the named revision of the set's run; the membership digest never
    includes assessments).
  - `output_assessment`: immutable judgments bound to their subject's run and to an exact revision
    digest, a set's membership digest, or a member the named index revision lists; never by the
    subject's (or any set member's) producer; a later one replaces an earlier one only through
    `supersedes`.
  - `obligation_fulfillment`: immutable decisions per pinned set and promise revision the set
    pinned (the same decision is recorded once); `obligation_association_step`: reminder, auto-association, ambiguity repair and
    block, at most once each per invocation and promise.
  - `invocation_finalization.outcome_basis` gains `declared_obligations` (the new default) and
    `no_declared_obligations`; `submission_coverage` stays readable for rows written before.

All eleven tables carry the installation/application/tenant scope in every key and foreign key, forced
row security, comments and runtime grants without DELETE (column-limited UPDATE only on the two

protocol stays `mission-control-runtime/1`. `scripts/prepare_release_170.py` reproduces the input
tree from the built 1.6.0 inputs. Proof: `tests/integration/postgres/test_sprint_oc_release_170.py`
(fresh install and upgrade from 1.6.0 with preserved receipts, verify and idempotent re-apply,
